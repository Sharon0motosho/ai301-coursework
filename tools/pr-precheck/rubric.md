# Rubric: is this pull request ready to submit?

Every check reads the candidate PR against three things: **the plan**
(the accepted plan in the plan context, including its in-scope items,
its "not in scope" list, its files list, its test plan, and any
recorded deviation), **the issue** (body and thread highlights), and
**the repo's standards** (the repo-facts block's `pull requests:` and
`contribution policy` lines; live, the PR template and
`docs/CONTRIBUTING.md`). "The diff" means every file and hunk in the
candidate PR's diff; "the description" means the PR title and
description; "the evidence" means the test-evidence section (live: the
before/after output pasted in the draft description).
`references/evidence-guide.md` says where each of these lives, and
`procedure.md` says in what order to gather them and run these checks.

A **disclosed shortfall** is a sentence in the description (or a
deviation recorded in the plan) that names something the PR does not
do, did not verify, or does differently from the plan, and says why.
Several checks below accept a disclosed shortfall in place of the
missing thing; none of them accepts a shortfall only the diff or the
evidence reveals.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-within-plan | Every changed file and every hunk in the diff, read against the plan's in-scope items, files list, "not in scope" list, and any recorded deviation | Mark each hunk as one of: (a) the fix the plan describes, (b) a test for that fix, (c) a changelog, release-note, or docs entry for the fix that the plan or the repo's contribution asks call for, or (d) a change named and explained in a disclosed shortfall/deviation. Pass when every hunk is (a)-(d). Fail when any hunk is none of them: a refactor or rewrite of code the fix does not need, a dependency or version bump the plan does not name, a new option/feature, a change to a file or area the plan lists as "not in scope", or a second unrelated fix. One such hunk is enough to fail, however small, and however correct the rest of the diff is. | required |
| plan-delivered | Each in-scope item the plan commits to (each approach step, each failure mode or case the plan says the fix covers, each file it says will change), read against the diff; and the mechanism the plan chose, read against the mechanism the diff implements | Pass when every committed item appears in the diff using the mechanism the plan chose, or is named in a disclosed shortfall/deviation. Fail when a committed item is missing from the diff with no disclosure (a named failure mode left unfixed, a promised regression test absent, a listed file untouched), or when the diff solves the problem a different way than the plan (catching the error instead of preventing it, a different layer, a different file) with no recorded deviation. | required |
| description-matches-diff | Every claim in the description about what the PR changes ("implements the plan exactly", "no changes beyond it", "tests added", "changelog entry added", "fixes both cases", the list of changed areas), read against the diff | Pass when every such claim is true of the diff. Fail when any claim is contradicted by the diff (claims "no other changes" while the diff carries an unrelated hunk; claims tests or a changelog entry the diff does not contain; claims a case is fixed that the diff does not touch), or when the description describes a different change than the diff makes. Claims about test outcomes belong to the two evidence checks below, not here. | required |
| repro-re-run | The evidence, read against the plan's test plan: each reproduction case the test plan names (every failing input or failure mode, plus any control) and its stated expected-after result | Pass when, for every reproduction case the plan's test plan names, the evidence shows that case re-run on the branch: the command or steps, and the observed after-result, and that result is the one the plan expected. For the issue's failing case(s) the after-result must be concrete (pasted output, an exit code, a printed value, a named test passing); a control or smoke check may be reported in one specific sentence saying what was observed ("the `-j 64` control runs unchanged"). A case not shown still passes if a disclosed shortfall names it as not run and says why, as long as at least one of the issue's failing cases is shown with a concrete after-result. Fail when there is no evidence; when the evidence is only generic ("tests pass", "works for me", "CI is green", "should fix it"); when a named failing case is silently missing; when the shown after-result differs from the plan's expected-after; or when the evidence re-runs a different input than the repro. | required |
| repo-checks-run | The repo's own checks: any test suite, linter, formatter, or CI requirement named in the repo-facts block, the contribution asks, the plan's test plan, or (live) CONTRIBUTING.md and the PR template; read against the evidence and the description | If no repo check is named anywhere in the package, pass. Otherwise pass when the evidence or description names each such check as run on the branch and states its outcome ("`cargo test` passes (614 tests)", "the full format suite passes", "`make lint` clean"). A failing or skipped check passes only when the description says which one, what failed, and why it is not caused by this change. Fail when a named check is never mentioned, when its outcome is not stated, or when it is reported as failing with no explanation. | required |
| reviewable-diff | The diff's added and removed lines, and the files it touches | Pass when every changed line serves the change: nothing a reviewer must read past to find the fix. Fail on any debris: debug output left in (print/console.log/dbg!/temporary logging), commented-out code, new TODO/FIXME/XXX markers, merge-conflict markers, stray or generated files (backups, `.orig`, `.DS_Store`, local config, build output), reformatting or reordering of lines the fix does not change (whitespace churn, line joins/splits, collapsed or expanded blocks, import reshuffles), or renames the fix does not need. Formatting applied only to lines the fix itself adds or changes is not debris. | required |
| template-and-asks | The repo-facts block's `pull requests:` line (template sections, checklist items, title convention, required entries) and the contribution asks (changelog entry, issue reference, tests with behavior changes, gating preconditions such as an approved discussion or a vouch), read against the title, description, and diff | List every ask that applies to this PR. Pass when each one is honored: a template section present with content specific to this PR (or marked "n/a" with a reason), a required entry (changelog, whatsnew, release-notes section) present in the diff or description, an issue reference present when asked, a title convention followed when asked, every checklist box ticked as done backed by the diff or evidence, and every gating precondition shown met or shown not to apply. If the repo states no template and no asks, pass. Fail when any applicable ask is visibly ignored: a required section missing or holding only placeholder text, a required entry absent, a checkbox claimed that the diff contradicts, or a PR opened in a category the repo says it does not accept (new features, linter updates, PRs without an approved discussion) without the stated precondition. | required |
| ai-disclosure-when-required | The repo-facts block's contribution policy (live: CONTRIBUTING.md, AI_POLICY.md, the PR template, and the course rule in `scope.md`), read against the description. Treat every package as AI-assisted work. | First decide what the policy requires of a pull request. If it requires disclosing AI use for PRs or "all AI usage in any form" (live, in Path Review: always, because the course requires an AI-use disclosure on every PR), pass only when the description discloses AI assistance with the tool named and the extent of what it did; a vague mention ("had AI look at it") fails when the policy asks for tool and extent. If the policy has no AI rule, or regulates only issue comments, pass. | required |
| maintainer-direction-honored | The thread highlights' maintainer, owner, member, or collaborator comments (a requested or rejected approach, a restated project rule, a pointer to existing code or an open PR), read against the diff and the description | If the thread holds no such direction, pass. Otherwise pass when the PR follows the direction, or the description names it and explains why it departs. Fail when the diff does what a maintainer said not to do (uses an approach they rejected, breaks a rule they restated in the thread) or ignores a direction they gave, and the description never mentions it. | required |
| title-says-the-change | The PR title, read against the diff | Pass when the title names the behavior the PR changes in words a reviewer could check against the diff ("Reject --threads values above a sane cap instead of panicking"). Fail when it is generic ("fix bug", "update"), names a different change than the diff, or is an exclamation. | preferred |

## Verdict rule

`accept` (ready to submit) when every `required` check passes.
`reject` (hold) when any `required` check fails. `unclear` counts as
`fail`: a fact the grader cannot verify from the package is a fact a
reviewer cannot verify either. `preferred` checks never change the
verdict; they are reported so the author knows what would make the PR
stronger. The deciding check for a reject is the first failing
`required` check in table order.
